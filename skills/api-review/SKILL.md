# API Review

호출자가 요청을 구성하고 응답으로 다음 동작을 수행할 수 있는지 검토한다. 필드가 서버에 존재한다는 사실보다 **클라이언트가 그 값을 받아야 하는 구체적인 이유**를 확인한다.

## 검토 범위와 기준

사용자가 지정한 API와 관점을 기준으로 현재 요구사항, 채택된 결정, 공통 API 규칙을 읽는다. 실제로 구현된 동작과 승인된 설계를 초안이나 테스트 편의를 위한 선택과 구분한다. 응답 형식과 HTTP 상태 정책은 해당 프로젝트의 규칙을 따른다.

리뷰 요청은 읽기 전용으로 수행한다. 수정도 요청받았다면 승인된 범위까지 반영한다. 특정 필드 제거와 다른 API의 제거 후보 보고를 함께 요청받았다면, 추가 후보는 수정하지 않고 보고한다. 앞선 대화에서 받은 수정 권한은 그대로 적용한다.

## 응답 필드의 사용처

응답 필드가 실제 호출 코드에서 화면이나 후속 요청으로 전달되는 경로를 추적한다. 이름 검색만으로 끝내지 말고 구조 분해, 객체 전달, 공유 상태, 직렬화와 변환도 확인한다.

- **화면과 판단:** 어떤 값이 표시, 분기, 계산, 정렬 또는 페이지 처리에 쓰이는가?
- **후속 처리:** ID, 버전, 토큰과 시각 값이 후속 요청, 캐시 또는 동시성 검사에 필요한가? 화면에 표시하지 않는다는 이유만으로 제거하지 않는다.
- **이미 가진 값:** 경로, 선택 상태, 인증정보로 알고 있는 값을 다시 반환한다면 응답 대조나 다른 구체적인 사용처가 있는가?
- **객체 전체 반환:** 화면에는 이름만 필요한데 내부 식별자와 다른 속성까지 함께 보내고 있는가? 서버가 세션 토큰으로 회원을 식별할 수 있다면 회원 객체를 클라이언트에 전달할 별도 이유가 있는가?
- **다른 소비자:** 같은 자료형을 쓰는 다른 API와 클라이언트를 확인하고, 진단·영수증·복구 등에 쓰이는지도 살핀다. 한 응답에서 쓰이지 않는 필드를 공통 자료형 전체에서 삭제하지 않는다.

예를 들어 상품 응답의 `id`가 캐시 키이고 `version`이 다음 변경 요청에서 충돌을 검사하는 데 쓰인다면 둘 다 사용 중이다.

미구현 기능의 필드 필요성은 승인된 화면과 호출 흐름으로 판단한다. 테스트나 fixture에서 필드를 기대하거나 DB에 해당 컬럼이 필요하다는 사실만으로 공개 응답에도 그 필드가 필요하다고 판단하지 않는다.

## 요청 구성

호출자가 필수 값을 넣을 위치와 형식을 명확히 알 수 있는지 확인한다. 특히 인증키, 일회성 확인값과 사용자 세션이 각각 무엇을 확인하기 위한 값이며 누가 전달하는지 구분한다. 필드의 필수 여부, null 허용 여부, 형식·단위·시간 기준을 확인하고, 이를 어긴 입력의 처리 결과도 살핀다.

ID나 상태 값이 나오면 정의와 사용 조건을 실제로 찾아본다. 생성 규칙에서 이미 결정되는 성질을 별도 제약처럼 반복하는지 살핀다. 같은 요청이 여러 오류 조건에 해당할 때 어떤 오류를 우선 반환하는지도 확인한다.

## 응답 해석

검토 범위의 각 API에서 성공, 업무 실패, HTTP 오류가 발생했을 때의 HTTP 상태·본문·헤더를 대조한다. 공통 정의를 참조한다면 실제 내용을 읽고 해당 응답에도 적용되는지 확인한다.

- 응답 필드의 위치, 자료형, 필수 여부, null 조건과 의미가 명확한가? 예시만 있고 스키마나 본문 정의가 빠진 부분은 없는가?
- `data: null`인 JSON 응답과 본문이 없는 응답을 구분하는가? 업무 데이터가 없는 성공도 프로젝트 규칙에 따른 응답 예시로 확인하며, JSON을 반환한다면 전체 본문을 확인한다.
- HTTP 오류 본문도 프로젝트의 공통 규칙에 맞게 정의되어 있는가? HTTP 상태와 본문의 오류 코드가 같은 오류 상황을 가리키는가? 프레임워크가 만드는 오류도 정의된 범위에 포함되는지 살핀다.
- 정상 리다이렉트, HTML 화면, 파일 응답과 외부 제공사 응답은 각 인터페이스의 규칙으로 판단한다. 공통 JSON 형식을 적용할 범위를 확인한다.

응답 형식의 변경을 제안할 때는 기존 호출자와 공통 규칙에 미치는 영향을 설명한다. 코드·메시지·추적 ID 같은 필드를 관례만으로 추가하지 않는다.

## 호출 흐름

정상 흐름과 실제로 발생 가능한 실패·중복 호출·만료·늦은 응답을 추적한다. 누가 어떤 조건을 확인하고 무엇을 바꾸며, 호출자가 결과를 받은 뒤 어떻게 진행하는지 확인한다. 상태 값의 의미와 상태 전이 조건을 구분하고, 전이가 복잡하면 다이어그램이 이해를 돕는지 검토한다. 재시도, 백오프, 새 상태나 저장소는 이를 필요로 하는 운영 상황이 있을 때 제안한다.

## 설명 배치

제목은 독자가 겪는 상황으로 쓴다. 예를 들어 화면 새로고침을 설명하는 절을 내부 자료형이나 문맥 복원 용어로만 이름 짓지 않는다.

호출 방법은 API 명세에, 내부 처리와 저장 순서는 설계 문서에 둔다. 같은 정의를 여러 곳에 복사하거나 이전 설계를 해명하는 문장을 남기는 대신 현재 동작과 필요한 참조로 정리한다.

## 명세와 구현 대조

Markdown과 OpenAPI에 정의된 경로, 인증, 필드, 필수 여부, null 허용 조건, HTTP 상태, 오류 코드와 예시를 대조한다. OpenAPI의 응답 또는 스키마가 참조로 정의되어 있으면 참조 대상까지 읽는다. 예시의 값이 스키마가 허용하는 범위에 드는지도 확인한다.

구현이 있으면 문서와 실제 요청 처리·응답 생성·클라이언트 사용을 비교한다.

수정한 경우에는 필드 정의, `required` 목록, 예시, 변환 규칙, 연결 문서와 관련 호출 코드를 함께 맞춘다. 공개 필드 제거와 서버 내부 식별자·상태·저장 규칙의 제거를 구분한다. 제거 대상 필드를 만들기 위해서만 존재하는 조회나 DTO가 있는지도 확인한다. 역사적 원문과 다른 API에서 필요한 자료형은 보존한다. 저장소의 관련 검사와 변경에 맞는 검증을 실행한다.

## 결과 보고

확정된 문제, 사용처를 찾지 못한 제거 후보, 확인이 필요한 설계 차이를 구분해 영향이 큰 순서로 보고한다. 각 항목에는 선언 위치, 사용처를 조사한 근거, 구체적인 영향과 최소 수정 방향을 포함한다.

필드를 미사용으로 판단했다면 확인한 클라이언트와 설계 범위를 밝힌다. 자료가 없거나 다른 소비자가 불명확하면 그 한계를 적는다. 검토한 API 범위, 관련 문서의 중복과 의미를 검토한 결과, 실행한 검증과 그 결과를 짧게 덧붙인다. 구조 검사 통과와 호출 용도·동작의 타당성 검토를 구분하고, 문서만 고쳤다면 구현 완료로 보고하지 않는다. 문제가 없으면 그 사실을 보고한다.
