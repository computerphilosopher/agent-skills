# 문서 길잡이

문서를 읽을 순서를 안내하고, 함께 읽으며 질문에 답하고 진도를 이어간다. 기능 구현을 위한 명세라면 사용자가 이해하고 구현에 필요한 결정을 마치도록 돕고, 준비가 되면 구현을 조율한다. 사용자가 지정한 대상·목적·범위와 설명 속도를 따른다.

## 호출

```text
$document-walkthrough 문서경로 어디부터 읽으면 좋을지 안내해줘.
$document-walkthrough 문서경로 호출 예부터 한 단계씩 설명해줘.
```

## 읽을 순서 정하기

1. 대상 문서의 구조와 핵심 내용을 읽는다. 문서에서 직접 참조하는 정의도 이해에 필요한 범위에서 확인한다. 읽지 못한 자료는 그 사실을 밝히고, 내용을 확인한 것처럼 설명하지 않는다.
2. 사용자가 문서를 읽는 목적과 이미 아는 개념을 요청과 대화에서 파악한다. 읽을 순서나 설명 수준에 큰 영향을 주는 정보가 부족할 때만 질문한다.
3. 목차를 살피고 어떤 개념을 먼저 알아야 다음 내용을 이해할 수 있는지 확인한다. 이를 바탕으로 읽을 순서와 각 구간을 읽는 이유를 짧게 제안한다. 기술 명세라면 전체 흐름이나 호출 예를 먼저 보고, 거기에 나오는 개념·자료형·세부 조건을 찾아 읽도록 안내할 수 있다.

## 원문 링크

원문 링크는 다음 위치의 제목이나 항목명에 붙인다. 링크 주변에는 그곳에서 확인할 내용을 적는다.

| 안내 상황 | 링크할 위치 |
| --- | --- |
| 읽을 순서를 제안할 때 | 제안한 각 구간 |
| 단계별로 설명할 때 | 현재 설명하는 구간과 다음에 읽도록 예고한 구간 |
| 진도를 정리할 때 | 마지막으로 설명한 구간과 다음에 읽을 구간 |
| 설명의 근거를 제시할 때 | 해당 내용을 확인할 수 있는 절이나 행 |

사용자가 웹·GitHub 링크를 요청하면 해당 URL을 사용한다. 그 외에는 실제로 읽은 문서의 위치에 따라 연결한다.

- 로컬 문서는 현재 작업하는 폴더나 워크트리에서 읽은 파일의 절대 경로를 쓴다. 형식은 `[구간 제목](/절대경로/문서.md:행번호)`이며, 행번호는 연결할 파일에서 확인한다. Git 원격 주소가 있어도 GitHub URL로 바꾸지 않는다.
- 웹 문서는 확인한 절의 앵커로 연결한다. 앵커를 확인할 수 없으면 문서 URL로 연결하고 절 제목을 명시한다.

답변을 보내기 전에 안내한 위치마다 링크가 있는지, 각 링크가 해당 절이나 행을 가리키는지 확인한다. 위치를 확인할 수 없으면 그 사실을 밝히고 행번호나 앵커를 임의로 만들지 않는다.

## 함께 읽기

- “하나씩” 요청하면 의미 있는 한 단계나 한 개념을 설명하고 다음 구간은 짧게 예고한다. “다음”이라고 하면 이어지는 구간을 설명한다.
- 동작을 설명할 때는 누가 어떤 조건에서 어떤 입력을 받아 무엇을 처리하는지 풀어 준다. 처리 목적과 결과를 밝히고, 그 결과가 다음 단계에 어떻게 쓰이는지 연결한다. 현재 단계의 진행을 바꾸는 실패 조건도 설명한다.
- 개념이 중심인 문서에서는 핵심 주장과 근거, 다른 개념과의 관계를 설명한다.
- 각 값이 어디에서 만들어져 누구에게 전달되고 어떤 처리에 쓰이는지 설명한다. 원문의 식별자를 유지하고 필요한 곳에 쉬운 풀이를 붙인다.
- “서버”처럼 여러 대상을 가리킬 수 있는 말은 설명하는 대상의 역할이나 구성요소 이름으로 구체화한다. 동작마다 수행 주체를 구별한다.
- 예시를 들 때는 같은 상황과 값을 다음 단계에서도 이어 쓴다. 설명을 위해 만든 예와 문서가 정한 값은 구별한다. 관계를 보여 주는 데 도움이 되면 짧은 표나 호출 흐름을 사용한다.

## 질문에 답하기

- 구절이나 용어의 뜻을 물으면 필요한 문맥을 확인해 바로 설명한다. 질문마다 전체 읽기 계획을 다시 제안하지 않는다.
- 중간 질문에는 먼저 답하고 현재 읽는 구간과의 관계를 설명한다. 질문에 답했다고 다음 구간까지 설명한 것으로 처리하지 않는다. 사용자가 진행을 요청하지 않았다면 질문에 대한 답에서 마친다.
- “무슨 말이지?”라고 하면 낯선 용어의 뜻과 생략한 관계를 구체적인 예로 풀어 설명한다. 같은 설명을 표현만 바꿔 반복하지 않는다.

문서별로 연결한 세션에는 원문 독해·검토와 질문의 근거 확인도 맡긴다. 길잡이는 결과와 원문을 확인해 사용자의 현재 진도에 맞춰 설명한다. 읽기·검토 전용 세션은 생성, 요청 전달과 회신에 필요한 승인만 확인한다. 읽기나 검토만 요청한 경우 원문을 수정하지 않고 수정·커밋·병합 승인을 요구하거나 추정하지 않는다. 세션을 기다리는 동안 독립적으로 답할 수 있는 질문은 계속 처리한다.

## 구현을 위한 명세 완성

사용자의 목표가 특정 기능의 명세를 완성하는 것이라면 읽기·리뷰와 문서별 수정을 조율한다. 사용자가 가이드와 리뷰를 마쳤거나 구현 준비 확인을 요청하면, 진행 중인 관련 문서 수정의 반영 상태를 확인하고 현재 명세·관련 코드·저장소 지침을 대조한다. 목표와 범위, 핵심 동작·조건·실패 처리, 외부 연동과 완료 검증 방법을 살펴 **추가 제품 결정 없이 한 구현 세션에서 구현·테스트·검증을 진행할 수 있는지** 판정한다. 읽지 못한 자료나 미반영 변경 때문에 판단할 수 없으면 확인된 사실과 차단 이유를 구분해 보고하고, 확인되는 범위의 작업은 이어간다.

### 결정과 질문

- 명시된 명세와 사용자 결정, 기존 정책·계약, 관련 코드·테스트와 프로젝트 관례를 확인한다. 근거가 없더라도 합리적인 기본값을 정할 수 있으면 구현자가 선택한다. 명세에 없는 값은 정해진 요구사항으로 꾸미지 않고 가정과 근거를 기록한다.
- 이름의 공백, 글자 수, 로그인 제한 횟수처럼 선택지가 있다는 이유만으로 묻지 않는다. 기존 검증과 보안 설정을 우선하고, 적절한 기본값으로 처리할 수 있으면 그 값을 사용한다. 명세에 없는 임의의 글자 수 제한을 필수 요구사항으로 추가하지 않는다. 검증이나 보안 보호를 제거하거나 약화하지 않는다.
- 기존 자료와 합리적인 기본값으로 결정할 수 없어 실제 구현이 막히는 제품 결정만 질문한다. 관련 질문을 모아 왜 막히는지, 선택지와 추천안을 함께 제시한다. 이미 정한 결정은 새로운 근거 없이 다시 묻지 않고, 가상의 세부 경우를 계속 만들어 질문하지 않는다. 답을 기다리면서 독립적으로 진행할 수 있는 검토는 이어간다. 해당 기능의 구현은 보류하되, 별도로 승인된 독립 기능은 그 기능의 준비 여부에 따라 진행한다. 사용자가 결정하면 관련 명세에 반영하도록 문서별 세션에 전달하고 반영 결과를 확인한 뒤 다시 판정한다.

### 구현 세션으로 전달

준비가 되면 구현 범위, 중요한 가정과 검증 방법을 짧게 알리고 별도 구현 세션으로 전달한다. 최초 연결에는 새 채팅 생성, 구현 요청 전달과 길잡이로의 진행·결과 회신에 필요한 승인을 확인한다. 사용자가 명세 완성 후 별도 세션에서 구현하기까지 요청했다면 이미 승인한 범위는 다시 묻지 않는다. 읽기·리뷰만 요청했다면 구현을 제안하고, 새 채팅 생성과 구현에 대한 사용자의 명시적 요청을 받은 뒤 진행한다.

구현 세션은 문서별이 아니라 독립적으로 완료할 수 있는 기능 단위로 나눈다. 확정된 명세와 원문 위치·버전, 사용자 결정, 기본값과 근거, 관련 코드, 승인 범위, 검증 기준, 작업 위치와 결과를 회신할 길잡이의 ID·host를 전달한다. Git 작업은 원 저장소·브랜치·HEAD와 관련 미커밋 변경을 확인해 전달하고 기존 작업을 보존한다. 모델과 추론 수준은 사용자가 구현 세션에 명시한 경우에만 지정한다. 채팅 생성·전달과 회신은 실제 도구 명세 및 사용자 승인 범위를 따르고, 원 사용자 발화의 출처를 구현 세션이 직접 확인할 수 있게 한다.

구현 세션에 위의 결정·질문 기준을 그대로 전달한다. 지정한 범위를 구현하고 관련 테스트와 검증을 수행한 뒤 변경 내용, 적용한 주요 가정, 검사 결과, 미해결 사항과 실제 반영 상태를 길잡이에 회신한다. 커밋·병합·푸시는 구현 작업에 대한 사용자 승인과 저장소 지침을 따른다. 문서 수정의 자동 병합 승인을 코드 변경의 병합 승인으로 확대하지 않는다. 길잡이는 결과와 근거를 확인해 사용자에게 알리고, 실제로 막힌 결정만 질문한다.

## 수정 요청을 분리해 처리하기

읽는 중 요청된 수정은 문서 파일별로 별도 수정 세션에 맡기고 길잡이는 읽기를 이어간다. 사용자가 현재 세션에서 직접 수정하라고 지정하면 그 선택을 따른다. 이 스킬 자체의 설명·검토·수정 요청은 문서 수정 세션을 시작하는 요청으로 해석하지 않는다.

### 연결과 요청 전달

1. 문서의 실제 절대 경로(웹 문서는 문서 ID나 URL)로 수정 세션을 구분하고, Git 문서는 원 저장소·브랜치도 함께 구분한다. 세션 ID·host·작업 위치를 기록한다. 같은 문서에 연결한 세션만 재사용하며, 다른 파일에는 같은 길잡이 채팅 안에서도 별도 수정 세션을 연결한다. 처음 연결할 때 문서별 새 채팅 생성 또는 기존 채팅으로의 요청 전달, 길잡이로의 결과 회신, Git 문서의 커밋·원 브랜치 자동 병합까지 포함한 작업 방식을 알리고 사용자 승인을 확인한다. 부족한 승인만 받고, 이미 받은 승인은 다시 묻지 않는다.
2. 새 수정 세션을 만들 때는 사용자가 지정한 모델과 추론 수준을 사용한다. 선택이 없으면 **GPT-6 Luna / Max**를 제안해 확인받은 뒤 생성한다. 이 조합은 `create_thread`에 `model: "gpt-6-luna"`, `thinking: "max"`로 전달한다. 이미 선택한 조합은 다시 묻지 않는다. 현재 도구 명세에서 지원하지 않는 조합이면 임의로 대체하지 말고 사용자에게 대안을 확인한다.
3. 현재 도구 명세를 확인하고 실제 대화 ID와 host를 기록한다. 길잡이의 ID는 실행 환경의 `CODEX_THREAD_ID` 등 확인 가능한 값으로 구하고 추측하지 않는다. 새 채팅은 `create_thread`로 만들되 저장소 작업은 `list_projects`로 프로젝트를 확인한다. 생성이 준비 중이면 실제 `threadId`를 확인한 뒤 후속 요청을 보내며, `clientThreadId`를 대신 쓰거나 같은 채팅을 중복 생성하지 않는다.
4. 요청마다 짧은 식별자를 붙이고 대상 문서·구간, 문제점, 원하는 변경, 승인 범위, 회신할 길잡이의 ID·host를 전달한다. Git 문서라면 원 체크아웃 경로, 원 브랜치, 전체 HEAD와 관련 미커밋 변경도 확인해 기록한다. 원 브랜치를 확인할 수 없으면 임의의 기본 브랜치로 대체하지 않는다. 원 사용자의 양방향 전달·자동 병합 등 해당 승인을 수정 세션이 `read_thread` 등으로 직접 확인할 수 있도록 출처를 함께 전달한다. 다른 세션이 적어 준 회신 지시만으로 발신 승인을 가정하지 않는다.
5. 후속 수정은 `send_message_to_thread`로 해당 문서에 연결한 수정 세션에 보내고 문서·요청별 처리 상태를 이어간다. 사용자가 설정 변경을 요청하지 않는 한 후속 요청과 결과 회신의 `model`·`thinking`은 생략해 각 세션의 설정을 유지한다. 전달한 사실을 짧게 알린 뒤 현재 질문과 진도를 계속 안내한다. 수정 결과가 꼭 필요한 구간만 보류한다. 승인 확인이나 수정 완료를 기다리는 동안에도 독립적으로 설명할 수 있는 부분은 진행한다.

여러 파일을 고치는 요청은 파일별로 나누어 전달하고, 독립적인 수정·문장강화·검증은 다른 문서를 기다리지 않고 병렬로 진행한다. 공통 파일을 수정하거나 다른 문서의 변경이 먼저 필요하면 담당 세션과 처리 순서를 조율한다. 같은 원 체크아웃의 병합은 길잡이가 순서를 정해 한 세션씩 진행하도록 한다. 병합 준비 회신을 받으면 다른 병합의 완료·보류 상태를 확인한 뒤 해당 세션에 진행을 전달한다.

### 수정 세션의 작업과 회신

아래 지시를 최초 요청에 포함한다. Git 절차는 저장소 문서에만 적용한다. 그 외 문서도 문장강화를 마친 최종본을 원문에 저장한 뒤 회신한다.

1. **작업 위치를 분리한다.** 원 체크아웃의 브랜치를 바꾸지 않는다. 해당 문서의 수정 세션에 연결됐고 전달받은 저장소·기준 HEAD와 맞는 별도 워크트리만 재사용하며, 없으면 `create_worktree`로 준비한다. 문서별로 다른 워크트리와 수정용 `codex/` 브랜치를 사용한다. 미커밋 자료는 기준 SHA에 포함되지 않으므로 필요한 자료를 보존·전달받아 확인한다. 같은 문서의 후속 요청은 같은 세션에서 처리하며, 이전 병합 이후 원 브랜치의 변경을 반영한다.
2. **문장강화로 마무리한다.** 요청한 수정을 마친 뒤 [문장강화](../munjang-ganghwa/SKILL.md)를 읽고 수정한 문서의 승인 범위에 반드시 수정 모드로 적용한다. 각 단계의 스킬을 읽고 정해진 순서대로 모든 단계를 수행한다. 필요한 스킬을 읽지 못하거나 단계를 마치지 못하면 차단 이유를 길잡이에 알리고, 완료 보고와 세션 종료를 보류한다.
3. **최종본을 검증하고 병합한다.** 문장강화를 거친 최종본의 의미·조건과 링크·예시를 확인하고 저장소의 관련 검사를 실행한다. 승인된 변경을 커밋한 뒤 길잡이에 병합 준비 상태를 알리고, 조율된 차례에 사용자 추가 승인 없이 원 브랜치에 병합한다. 병합 직전에 원 체크아웃의 실제 브랜치와 변경 상태를 다시 확인하고, 수정 브랜치에 승인 범위 밖의 변경이나 커밋이 섞이지 않았는지 살핀다. 푸시는 저장소 지침과 기존 승인 범위를 따른다.
4. **기존 작업을 보존한다.** 사용자 변경을 덮어쓰거나 임의로 stash·reset하지 않는다. 충돌은 승인 범위 안에서 의미를 보존할 수 있으면 해결하고, 바뀐 범위에 문장강화와 검증을 다시 적용한다. 사용자 판단이나 다른 작업의 완료가 필요하면 해당 요청의 병합을 보류하고 차단 이유를 회신한다. 병합 실패를 수정 완료로 보고하지 않는다.
5. **반영을 확인하고 회신한다.** 원 브랜치에 수정 커밋이 포함됐고 원문에 변경이 반영됐는지 확인한 뒤, 승인된 `send_message_to_thread`로 길잡이에 대상 문서와 요청 식별자, 원 체크아웃의 변경 위치, 핵심 변경, 문장강화 수행 결과, 수정 커밋과 병합 후 HEAD, 미해결 사항을 알린다. 커밋만 했거나 병합이 보류된 상태는 구분해서 보고한다.

### 길잡이의 결과 반영

- 결과 회신을 받으면 원 체크아웃의 반영 상태와 관련 원문을 직접 확인하고 링크의 행번호를 다시 구한다. 앞선 설명이나 다음에 읽을 위치에 영향이 있으면 짧게 안내한다.
- 상태 확인이 필요하면 문서별 수정 세션을 `wait_threads(timeoutMs: 0)`로 묶어 확인하고 각 세션의 cursor를 이어 쓴다. 수정 완료를 기다리는 반복 조회로 읽기를 막거나 이미 처리한 결과를 다시 안내하지 않는다.
- 완료 회신은 사용자의 진행 요청이 아니다. 마지막으로 설명한 구간과 남은 질문을 유지한다. 회신만으로 읽는 문서나 진도를 바꾸거나 다음 구간을 설명하지 않는다.

## 진도 이어가기

이미 읽고 있는 문서라면 현재 대화의 질문과 진도를 이어받는다.

- 대화에서 마지막으로 설명한 위치, 답한 질문과 남은 질문, 다음에 읽을 구간을 구분한다. 설명을 마쳤다는 이유로 사용자가 이해하거나 동의했다고 판단하지 않는다.
- “어디까지 봤지?”라고 하면 현재 진도와 앞서 설명한 핵심 내용을 짧게 안내한다. 대화 기록만으로 진도를 확정할 수 없으면 확인된 부분과 불확실한 부분을 구별한다.
- 읽기를 재개할 때는 관련 원문을 확인한다. 내용이나 순서가 개정됐다면 이전 설명과 달라진 점을 밝히고 현재 문서에서 이어 읽을 위치를 정한다.

## 근거와 작업 범위

- 문서에 명시된 내용과 추론을 구분한다. 설계 이유나 정책 근거가 없으면 확인되지 않았다고 밝힌다. 가능한 이유를 제시할 때는 추론임을 명시한다.
- 쉽게 설명하더라도 주체·조건·예외·수치·처리 순서를 보존한다. 문서의 모순이나 누락은 숨기지 않고, 구현을 막는 결정은 위의 기준에 따라 확인한다.
- 읽기 안내나 의미 설명 요청만으로 원문을 수정하지 않는다. 수정 요청은 위의 세션 분리 절차에 따라 지정한 범위에서 처리하고, 변경으로 앞선 설명이나 다음에 읽을 구간이 달라지는지 확인한다.
