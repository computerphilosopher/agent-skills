# 문장 표현 리뷰

독자가 단어 사이의 관계나 문장의 뜻을 추측하게 만드는 표현을 찾아 원래 뜻을 유지하며 다듬는다. 기본은 수정이다. `review`를 지정하거나 명시적으로 검토만 요청하면 원문을 유지하고 발견 사항을 보고한다.

## 검토 범위

사용자가 지정한 범위에서 본문과 제목, 표 안의 문장, 주석과 예시를 읽는다.

문서에 정해진 정책과 설계, 원문 인용, 공식 명칭과 역사적 기록을 보존한다. 필요한 정보가 없어 뜻을 확정할 수 없는 부분은 확인할 질문으로 남긴다.

## 검토 방법

1. 대상 독자와 글의 목적, 적용되는 작성 지침을 확인한다. 각 문단이 답하는 질문을 파악한다.
2. 동작을 설명하는 문장은 누가 어떤 조건에서 어떤 대상을 어떻게 처리하며, 그 결과 무엇이 바뀌거나 반환되는지 풀어 읽는다. 이 관계가 문장과 관련 문맥에서 확인되지 않으면 문제 후보로 삼고 아래 기준으로 원인을 파악한다. 검토 범위 안의 주변 문맥과 직접 연결된 설명에서 같은 원인의 문제를 함께 확인한다. 단어가 같다는 이유만으로 일괄 수정하거나 모든 요소를 문장마다 반복하지 않는다.
3. 수정안으로도 독자가 같은 조건에서 같은 행동과 결과를 이해할 수 있는지 확인한다. 동작 대상과 수치의 단위, 예외를 보존하고, 일부 조건의 규칙이 전체로 확대되지 않게 한다. 수정안에 원문이 정하지 않은 의미를 보태지 않는다.
4. 수정안과 앞뒤 문맥을 함께 읽는다. 수정안에서도 생략한 주어나 목적어가 다른 동작에 잘못 이어지지 않는지 확인한다. 지적한 문장과 같은 유형의 문제가 검토 범위 안에 남아 있는지 확인한다. 수정 모드에서는 확인한 수정안을 문서에 반영하고 관련 문맥을 다시 읽어 의미 보존 여부를 확인한다.

## 검토 기준

### 명사 나열과 겹친 명사구

명사가 이어진 표현은 명사 사이의 관계를 풀어 읽는다. ‘서버 상태 저장’은 누가 어떤 상태를 어디에 저장하는지, ‘카드 요청 구성’은 어떤 값으로 어떤 요청을 만드는지 확인한다. ‘현재 입력’처럼 대상을 짐작하게 하는 포괄적인 이름도 확인한다.

‘준비한다·사용한다·구성한다·반영한다’ 같은 서술어가 있어도 실제 행동이 드러나는지 확인한다. 주어나 조사만 보충해도 무엇을 하는지 불분명하면, 문맥에서 확인한 구체적인 행동으로 풀어 쓴다. 긴 수식어가 무엇을 꾸미는지 모호하면 수식어를 대상 가까이 옮기거나 문장으로 풀어 관계를 드러낸다.

대등한 항목을 나열했다면 각 항목이 어떤 역할을 하는지 확인한다. 같은 서술어로 묶었다면, 그 서술어가 모든 항목에 자연스럽게 적용되는지 확인한다. 대상과 행동을 한데 묶어 관계를 추측하게 하면 문장으로 풀고, 독립적으로 확인할 항목이면 목록으로 나눈다. 기호만 쉼표나 접속어로 바꾸는 것으로 끝내지 않는다. 명사의 개수나 특정 단어, 가운뎃점 사용 여부만으로 지적하지 않으며, 짧고 대등한 항목을 명확하게 묶는 나열은 유지한다.

### 문장 관계

- 독자가 알아야 할 동작과 처리 결과가 드러나는지 확인한다. 기술 문서에서는 계산·조회·저장·반환을 구별하고, 작업을 실행한 뒤 바뀌거나 유지되는 내용을 살핀다. 결론이나 처리 방향만 제시하고 필요한 정보를 생략했다면, 문맥에서 확인되는 내용을 보충한다. 설명의 수준은 문서의 목적과 대상 독자에 맞춘다.
- 독립적인 주장이나 여러 조건이 얽혀 있으면 의미 단위로 나눈다. 같은 결과나 상태 이름으로 묶었더라도 조건에 따라 바꾸거나 유지하는 내용이 다른지 확인한다. 조건과 결과, 원인과 효과를 가까이 두고, 차이를 비교해야 이해할 수 있으면 문장·목록·표로 나란히 배치한다.
- 번역투와 이중 피동, 겹친 완곡 표현이 이해를 어렵게 하거나 문장을 불필요하게 늘리는지 확인한다. 다시 쓸 때 가능성을 단정으로 바꾸거나 의무와 유보의 정도를 바꾸지 않는다.

### 용어와 참조

용어나 축약 표현이 대상 독자에게 충분히 설명되어 있는지 확인한다. 이름이 가리키는 대상과 수치의 단위, 기준 시점을 밝히고, 예상과 실제, 시점과 기간처럼 혼동하기 쉬운 개념을 구별한다.

참조 문서나 모듈 이름을 적었더라도, 무엇의 어떤 부분을 그곳의 어떤 정의에 맞추는지 확인한다. ‘입력’처럼 여러 대상을 묶은 말 때문에 관계가 불분명하면, 요청 본문과 쿼리 매개변수 등을 구별해 적는다. 구체화할 항목은 관련 문맥과 명세에서 확인한다. 문서의 위치를 안내한다면 그곳에 정의된 내용을 밝히고, 실제 동작을 설명한다면 수행 주체와 행동을 적는다.

명사를 나열하고 참조 링크로 문장을 끝내면서 관계 설명을 생략한 표현을 찾는다. 현재 내용을 이해하는 데 필요한 핵심 설명은 본문에 두고, 상세 내용은 해당 정의로 직접 연결한다.

- 문제: “HTTP 입력과 응답은 예약 API를 따른다.”
  수정 — 요청 본문과 응답 본문의 JSON 구조를 가리키는 경우: “요청 본문에 담을 JSON 필드와 자료형은 예약 API 명세에 정의되어 있다. 서버가 반환하는 JSON의 구조도 같은 명세에 정의되어 있다.”

서술어만 ‘정의한다’나 ‘적용한다’로 바꿨더라도 관계가 여전히 불분명하면 수정이 필요하다. 짧은 참조만으로 의미가 충분한 문장은 유지한다.

## 결과 보고

독자의 이해에 미치는 영향이 큰 항목부터 **[심각도] 위치 → 문제와 영향 → 수정 방향**으로 보고한다. 가능하면 짧은 수정안을 제시한다. 같은 원인의 지적은 묶는다.

핵심 의미를 잘못 이해하거나 잘못된 행동을 하게 하면 `critical`, 문맥을 확인해도 뜻을 확정하기 어려우면 `warn`, 의미는 명확하지만 읽기 부담을 줄일 수 있으면 `info`로 분류한다. 단순 취향이나 기호 사용만으로 지적하지 않는다. 명시적 필수 작성 규칙 위반은 심각도와 별도로 표시한다.

검토 범위와 한계, 남은 질문을 짧게 적고 열람하지 못한 자료는 미검토로 표시한다. 수정했다면 **위치 → 실제 변경 내용 → 이유**와 확인 결과를 보고한다. 링크·형식 검사 결과와 문장의 의미·가독성 검토 결과를 구분해 보고한다.

검토한 범위의 문서 상태를 다음과 같이 보고한다.

- **수정 필요:** 미해결 `critical`·`warn` 또는 명시적 필수 작성 규칙 위반이 있다.
- **선택적 개선 있음:** 필수 수정 항목 없이 `info`만 남았다.
- **지적 없음:** 미해결 지적이 없다.
