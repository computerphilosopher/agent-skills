# 코드검증

구현이 명세를 충족하는지, 테스트가 결함을 잡는지, 실제 실행 결과가 요구사항과 일치하는지 차례로 검증한다.

## 자동 실행

큰 기능을 구현한 뒤 완료를 보고하기 전에 이 스킬을 자동으로 실행한다. 여러 계층을 연결하는 기능, 새 사용자 흐름, 핵심 업무 규칙이나 상태 전이를 추가·변경한 작업이 대상이다. 변경 줄 수보다 동작과 의존 관계의 변화를 기준으로 판단한다. 문구·서식·문서만 고치는 작업이나 동작에 영향이 적은 작은 수정은 자동 실행 대상에서 제외한다.

자동 검증의 범위는 방금 구현한 기능의 요구사항, 변경 코드와 영향받는 호출부·테스트·사용자 흐름이다. 사용자가 더 넓은 범위를 명시했다면 그 범위를 따른다. 자동 실행에서는 승인된 구현 범위의 문제를 수정하는 `fix` 모드를 사용한다. 명시적인 `review` 호출이나 검토만 해달라는 요청은 소스·테스트·설정을 유지한다.

## 호출

| 호출 | 모드 |
| --- | --- |
| `$code-verification [대상]` | 검증: 코드와 테스트를 검토하고 관련 검사를 실행한다. |
| `$code-verification review [대상]` | 검증: 소스·테스트·설정을 유지하고 발견 사항을 보고한다. |
| `$code-verification fix [대상]` | 수정: 확인된 문제를 수정하고 다시 검증한다. |

기본은 검증 모드다. 수정 요청이 있으면 현재 대화에서 승인된 범위 안에서 수정한다. 명시적으로 검토만 요청받으면 검증 모드를 적용한다. 검증 모드에서는 소스·테스트·설정을 유지하고, 결함 검출 여부를 확인하려고 코드를 바꾸는 실험은 임시 복사본에서 수행한다.

검증 대상은 사용자가 지정한 파일·커밋·브랜치를 따른다. 대상을 생략하면 현재 대화에서 구현한 변경을 검증한다. 그런 변경이 없으면 미커밋 변경을, 미커밋 변경도 없으면 마지막 커밋을 검증한다. 요구사항·명세·승인된 결정과 저장소의 검사 규칙을 읽고, 대상·범위·모드를 각 단계에 동일하게 전달한다.

## Goal로 진행

사용자가 Goal 기반 검증이나 큰 기능 뒤의 Goal 자동 실행을 명시적으로 요청했다면 내장 Goal로 진행한다. 그 요청이 적용되는 작업마다 별도 확인을 반복하지 않는다. 일반 구현·검증 요청만으로 새 Goal 생성 권한을 추정하지 않는다. Goal 실행 요청이 없거나 사용자가 Goal 없이 진행하도록 지정해도 검증은 계속한다.

Goal 사용 요청이 적용되면 먼저 현재 채팅의 Goal을 조회한다.

- 현재 작업의 활성 Goal이 있으면 그 안에서 검증을 이어간다. 검증용 Goal을 중복 생성하거나 기존 목표를 교체하지 않는다.
- Goal이 없거나 이전 Goal이 완료됐다면 내장 Goal 생성 도구로 검증 목표를 활성화한다. 목표에는 대상·모드·검증 범위·작업 기록 경로와 다섯 단계의 항목 및 근거를 모두 확인한다는 완료 조건을 담는다. 예산은 사용자가 지정한 경우에만 설정한다.
- 현재 작업과 무관한 미완료 Goal이 있으면 완료나 교체로 처리하지 말고 충돌을 알린다. Goal을 바꾸지 않고 수행할 수 있는 검증은 계속한다.
- 내장 Goal 도구가 없으면 Goal을 활성화했다고 보고하지 않는다. 현재 검증을 이어갈 채팅에서 사용할 구체적인 `/goal` 명령과 미설정 상태를 알리고, 수행할 수 있는 검증은 계속한다.

각 재개 턴에서는 작업 기록을 읽고 다음 미처리 항목부터 검증한다. 중간 보고나 자동 검사 통과로 Goal을 완료하지 않는다. 검증 모드는 요청 범위의 검토와 근거 기록을 모두 마치면 절차 완료로 판정하고 발견한 결함을 보고한다. 수정 모드는 승인된 범위의 확인된 문제 수정과 재검증까지 마쳐야 한다. 기존 구현 Goal을 재사용했다면 그 Goal의 원래 완료 조건도 충족해야 한다. 이 조건들을 충족한 뒤 내장 Goal 상태를 완료로 갱신한다.

## 범위와 진행 기록

검증을 시작하기 전에 요청 범위의 요구사항, 관련 구현과 호출 경로, 테스트, 사용자 흐름을 목록으로 만든다. 전체 범위를 요청받았다면 일부 기능이나 주요 경로를 살펴본 것으로 대체하지 않는다. 범위가 넓으면 나누어 처리하고, 범위를 줄이거나 표본만 검토하는 것은 사용자가 요청한 경우에만 허용한다.

각 단계에 대해 검토할 항목과 상태, 코드·명세의 위치, 실행 결과 등 근거를 작업 기록에 남긴다. 상태는 미착수·진행 중·완료·막힘·해당 없음으로 구분한다. 항목을 추가로 발견하면 목록에 포함하고, 남은 항목을 다음 작업으로 이어간다. 코드에 결함이 있다는 판정과 그 항목의 검토를 완료했다는 상태는 구분한다.

## 실행

특정 관점만 요청받으면 해당 단계를 선택하고, 그 외에는 아래 단계의 적용 여부를 판단해 순서대로 진행한다. 각 스킬의 경로는 설치 목록에서 이름으로 찾고, 해당 단계를 시작할 때 `SKILL.md`를 읽는다.

검증 범위에 해당하지 않는 단계는 확인한 근거와 함께 해당 없음으로 기록한다. 검증 범위에 해당하지만 스킬·도구·실행 환경이 없어 수행하지 못한 항목은 막힘으로 기록하고, 같은 단계에서 진행할 수 있는 다른 항목을 검토한다. 작업 기록, 명세 대조 보고서, 브라우저 로그, 스크린샷 등 산출물은 사용자 지정 경로나 임시 경로에 저장한다.

| 순서 | 스킬 | 담당 |
| --- | --- | --- |
| 1 | `spec-to-code-compliance` | 명세의 요구사항별 구현 여부, 부분 구현·모순·누락과 문서에 없는 동작 검토 |
| 2 | `ponytail-review` | 변경 코드와 호출부의 결함, 보안·동시성·성능 위험, 테스트 누락과 불필요한 코드 검토 |
| 3 | [false-green-detector](../false-green-detector/SKILL.md) | 기대값의 명세 근거와 테스트가 잘못된 동작을 잡는지 검토 |
| 4 | `webapp-testing` | 로컬 웹앱의 사용자 흐름, 화면 동작, 브라우저 로그와 스크린샷을 통한 실제 동작 검증 |
| 5 | `verification-before-completion` | 마지막 수정 상태에서 관련 검사를 실행하고 출력과 종료 코드로 결과 확인 |

해당 단계의 범위 내 항목을 모두 검토하고 근거를 확인한 뒤 다음 단계로 넘어간다. 서로 다른 단계를 병렬로 진행하지 않는다. 한 단계 안의 독립 항목은 병렬로 검토할 수 있다. 문제 재현을 위해 앞 단계에서 검사를 실행할 수는 있지만, 이를 마지막 단계의 완료로 재사용하지 않는다.

각 단계의 발견 사항을 다음 단계에 전달한다. 명세 대조에서 얻은 요구사항별 결과는 구현 검토와 테스트 검토에 사용하며, 테스트가 없는 요구사항도 확인한다. 테스트 검토는 요구사항마다 어떤 테스트가 어떤 결과를 확인하는지 대조하고, 이를 확인할 테스트가 없는 경우도 기록한다.

처리할 수 있는 항목이 남아 있으면 검토를 이어간다. 부분 검토나 자동 검사 통과만으로 최종 보고를 하고 끝내지 않는다. 진행 상황을 묻는 요청에는 현재 상태를 알린 뒤 작업을 계속한다. 사용자가 정한 전체 작업 예산이나 중단 요청을 따르거나, 외부 자료·권한·사용자 결정 없이는 현재 단계의 남은 항목을 처리할 수 없을 때만 미완료 상태로 마친다. 이때 실제 차단 원인과 재개할 항목을 밝힌다.

### 명세 대조

명세가 있으면 요구사항별로 구현을 대조한다. 명세가 없거나 뜻이 불명확하면 구현에서 기대값을 만들어내지 말고, 명세 대조의 한계와 확인할 요구사항을 기록한다.

이 단계에는 스킬 본문뿐 아니라 원본 플러그인의 워크플로와 검토 에이전트가 필요하다.

- 워크플로 실행기가 있으면 원본 절차를 사용한다.
- 실행기가 없고 협업 도구가 있으면 플러그인 루트의 `workflows/spec-compliance.js`와 `agents/spec-compliance-checker.md`를 읽고 원본의 역할을 하위 에이전트에 배정한다. 요구사항마다 검토 에이전트를 배정하고, 명세에 없는 동작을 찾는 검토는 따로 수행한다. 발견 사항에 대한 반증은 이를 작성하지 않은 두 에이전트가 맡는다. 한 명은 코드를, 다른 한 명은 명세를 다시 읽고 발견 사항이 틀렸는지 확인한다. 원본의 결과 형식과 미검토·반증 실패 기록을 유지한다.

이 구성을 수행하지 못하면 명세 대조를 완료로 보고하지 않는다.

하위 워크플로의 한 번 호출이 전체 명세 대조의 완료를 뜻하지 않는다. `notChecked`, `checksFailed`, `unverified`, `unreadableDocuments`를 확인하고 작업 목록에 반영한다. 한 번에 처리할 수 있는 요구사항 수나 하위 호출의 예산 때문에 남은 항목은 다음 묶음이나 원본 checker로 이어서 검토한다. 확인할 수 있는 항목이 남아 있으면 명세 대조를 계속하고, 완료한 요구사항만 반복 검토하지 않는다.

### 웹앱 동작 검증

요청 범위의 요구사항과 구현에서 웹 화면·사용자 흐름이 있는지 확인한다. 검토하기 편한 코드나 검사 도구만을 골라 범위를 바꾸지 않는다. HTTP 통합 테스트는 브라우저 사용자 흐름의 검증을 대신하지 않는다. 웹 동작이 범위에 없다는 근거가 있을 때만 이 단계를 해당 없음으로 기록한다.

범위 내 사용자 흐름을 목록으로 만들고 Python Playwright로 웹앱을 조작해 결과를 확인한다. 정적 HTML은 로컬 파일로 열고, 서버가 필요한 앱은 설치된 스킬의 서버 실행 도우미로 구동한다. 화면이 로드됐다는 사실만으로 동작을 통과 처리하지 않는다.

### 검토 후 처리

수정 모드에서는 검토로 확인한 구현 결함과 테스트의 잘못된 기대값·누락을 승인된 범위 안에서 수정한다. 기대값은 명세에서 도출하고, 검증을 통과시키려고 요구사항이나 올바른 검증 조건을 완화하지 않는다. 수정으로 근거가 오래된 항목을 작업 기록에서 다시 진행 중으로 바꾸고, 영향받은 첫 단계부터 순서대로 재검토·재검증한다. 새 정책이나 설계 결정이 필요한 항목은 질문으로 남기고, 같은 단계에서 답이 없어도 검토할 수 있는 항목을 이어간다.

마지막에는 앞 단계들이 완료됐거나 근거를 갖춰 해당 없음으로 기록됐는지 확인하고, 저장소가 요구하는 검사와 변경에 맞는 테스트·빌드·타입 검사·린트를 실행한다. 검사 실패가 이번 변경 때문인지 불분명하면 가능한 범위에서 기준 버전과 비교하고, 구분할 수 없으면 원인 미확정으로 보고한다.

## 결과 보고

사용자의 언어로 마지막에 한 번 보고한다. 영향이 큰 발견 사항부터 **위치 → 문제 → 명세 근거 또는 재현 → 영향 → 수정 방향**으로 제시하고 같은 원인의 지적은 묶는다. 수정 모드에서는 실제 반영한 내용과 재검증 결과를 덧붙인다.

다섯 단계 모두의 상태와 전체 항목 수·완료 수·남은 항목, 확인한 근거를 제시한다. 해당 없음에는 범위에서 제외되는 근거를, 막힘에는 실제 차단 원인과 재개할 항목을 적는다. 실행한 명령과 결과, 발견한 결함과 남은 질문을 함께 보고한다.

모든 적용 단계의 항목을 검토한 경우에만 검증 절차 완료로 판정한다. 자동 검사 통과, 검증 절차 완료, 요구사항 충족을 구분한다. 절차를 마쳤더라도 확인된 결함이 남아 있으면 검증 통과로 판정하지 않는다. 미완료 상태로 마칠 때는 완료 표현 대신 중단 사유와 남은 작업을 명시한다.
